## Defect and scope

The previous `Supervisor::bind` opened and recovered the store before checking `operator.key`. A missing key generated another token, including for an existing journal. Real-binary regressions reproduced silent replacement authority and delivery recovery before invalid-key refusal. File validation and fsync alone did not address absence or ordering.

The historical startup slice changes only supervisor startup ordering and missing-key policy. The new recovery command below separately finishes publication of an intact original retained key; it does not rotate/adopt/reconstruct keys,activate archives,migrate Hermes profiles,change peer tokens,delete state or establish hostile same-user enforcement. An arbitrary syntactically valid replacement key still lacks independent authenticity; caller-supplied digest and attestation do not prove its history.

## Contract

- Acquire the existing store ownership lock before checking/provisioning a key. A competing opener must not inspect, sync or change the operator key.
- `Store::open_with_startup_guard` runs immediately after lock acquisition and database-name existence classification, before creating/opening the database file, SQLite, schema initialization, PRAGMAs or delivery recovery. The callback receives only whether the database name already exists and returns its validated local resource. A failing callback releases the lock and leaves the database unopened. Existing direct `Store::open` and offline migration semantics stay unchanged; the supervisor uses the guarded path.
- Missing key with any existing database name fails, including zero-length, legacy, malformed and v2 files. Never infer a new installation from an empty database or absent actor rows.
- New token creation is permitted only when the database name is absent and the private state directory contains exactly the owned `owner.lock` entry. Unknown entries, sidecars, pending publications or missing-key remnants refuse. Distinguish NotFound from other metadata errors.
- If a valid private key exists before database creation, reuse/sync it only when the directory contains exactly that key and `owner.lock`. This permits retry after key publication and before database initialization without fabricating another key. It does not independently prove that the token is original. Any additional entry, including actor files, sidecars or pending publications, requires explicit operator reconciliation, not guessed recovery.
- Reuse the bounded descriptor-based PrivateFile validation and file/parent sync before SQLite opens. Invalid, missing, unsafe or sync-failed key paths prevent listener creation and database recovery. No token contents/hashes appear in diagnostics or receipts.
- Preserve the normal successful startup recovery: only after the key guard passes does submitted mail become ambiguous. No IPC/operation/expiry/shutdown deadline is relaxed.

The state root and ownership lock may be created during a failed first startup; this is not filesystem-immutability. Refusal by the initial key guard leaves existing database/sidecar bytes and logical rows unopened and unchanged. After that guard passes, ordinary store opening can have effects; a later key recheck before listening detects selected substitutions but cannot roll back recovery or exclude a hostile same-user writer. Startup itself introduces no missing-key repair. Do not restore an archive or copy a historical key into live state merely to bypass refusal.
